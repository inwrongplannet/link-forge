# Migrations

Link Forge uses **Alembic 1.18.5** for database schema migrations, with autogenerate support tied to the SQLAlchemy ORM models.

## Configuration

### `alembic.ini`

- **Script location:** `migrations/` (relative to project root)
- **`prepend_sys_path = .`** — Ensures the project root is on `sys.path`
- **`sqlalchemy.url`** — Set as a placeholder in the INI file; overridden at runtime in `env.py` by `settings.database_url`

### `migrations/env.py`

The environment script:
1. Inserts the project root into `sys.path` so `app.*` imports work
2. Imports all models (`user`, `url`, `click`) to register them with `Base.metadata`
3. Overrides `sqlalchemy.url` with the value from `app.database.config.settings`
4. Sets `target_metadata = Base.metadata` for autogenerate support
5. Supports both online (live DB connection) and offline (SQL script generation) modes

### `migrations/script.py.mako`

The Mako template for new migration files. Generates standard Alembic migration boilerplate with `upgrade()` and `downgrade()` functions.

## Common Commands

### Generate a new migration (autogenerate)

```bash
alembic revision --autogenerate -m "description of change"
```

Alembic will compare the current `Base.metadata` against the database and generate upgrade/downgrade operations.

### Apply all pending migrations

```bash
alembic upgrade head
```

### Downgrade by one revision

```bash
alembic downgrade -1
```

### View current revision

```bash
alembic current
```

### View migration history

```bash
alembic history --verbose
```

### Generate SQL without executing (offline mode)

```bash
alembic upgrade head --sql
```

## Best Practices

1. **Always review autogenerated migrations** before applying. Alembic's autogenerate may miss or misinterpret certain changes (e.g., column renames vs. drop+add).
2. **Run migrations explicitly in production** rather than relying on `create_all()`. The bootstrap `create_all` is a convenience for development.
3. **Test downgrade paths** — ensure every migration can be reversed cleanly.
4. **Keep migrations atomic** — each migration should represent one logical change.
5. **Set `DATABASE_URL`** environment variable before running Alembic commands (the `env.py` reads it via `settings`).

## Docker Compose Startup

When running via Docker Compose, the application container automatically applies migrations before starting uvicorn:

```bash
alembic upgrade head || alembic stamp head && uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 4
```

- `alembic upgrade head` — applies any pending migrations
- `alembic stamp head` — fallback if the migration history is already current (stamps the version table without running operations)
- This ensures the schema is always up to date without requiring a separate init container
